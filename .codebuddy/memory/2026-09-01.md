# 2026-09-01 Magic Tarot Popup Fix (Round 2)

## Round 1 (reverted as `84db418`)

First attempt broke the popup entirely by forcing `min-width: 420px` on the
popup body. The popup went from "narrow + flashing" to "64x100 purple blob
with no text". Root cause for the collapse was actually `:root` typed as
`::root`, plus a UTF-8 BOM at the start of `popup.css`.

The user's screenshot showed the popup reduced to ~64x100 pixels with only
the three tool cards partially visible. Lesson: **never apply
`min-width: <px>` to the popup body in an extension popup**, it conflicts
with Chrome's own width clamping.

## Round 3 (committed this session) — TRUE root cause found

User reported popup STILL flickering/jumping after reload, with a screenshot
showing a ~50px-wide vertical strip (CJK text one char per line, h1
ellipsized to "魔…").

Root cause: `@media (max-width: 420px)` block at popup.css ~line 5936
(introduced 2026-05-22 in f90bce7) set
`:root { --popup-width: 100vw; --popup-height: 100vh; }`.

Fatal mechanics:
1. `max-width: 420px` is inclusive → fires at the popup's NORMAL 420px width.
2. Once viewport dips below 420px (first-frame race), 100vw locks body width
   to the too-small viewport → Chrome sizes window to min-content (~50px).
3. Below 420px the query still matches → permanently trapped in the strip.
4. 100vh height feedback loop → continuous reflow = the flickering.

Why "it worked before": racy first-frame sizing usually landed ≥420px where
100vw==420px is harmless. Recent sizing disturbances (viewport meta
reappearing, ::root typo) made the first frame fall below 420 and triggered
the trap.

Fixes applied:
- Deleted the whole `@media (max-width: 420px)` block; left a guard comment.
- (Earlier this session) removed `<meta name="viewport">` from popup.html
  again (it had reappeared); added nowrap+ellipsis to `.welcome-content h1`.
- Verified only remaining vw/vh is `max-height: 80vh` on the hidden modal
  (harmless). Card sizes are JS-inline; no CSS media fallback needed.

Lesson written to global rule:
`chrome-popup-no-viewport-media-query-RULE`.

## Round 4 (committed `796e406`) — second inclusive-boundary trap

User asked the popup's size. Declared 420x600, but ACTUAL was 420x500 because
`@media (max-height: 600px)` (popup.css ~1790) fired (inclusive: viewport is
exactly 600px) and set `--popup-height: 500px`. It converged in one step so it
never flickered — it just silently cost 100px of height. Deleted the block.

Popup sizing truth after Round 4: **420 x 600** is now really in effect.

Remaining media queries (both to be removed):
- `@media (max-width: 420px)` ~1790: INCLUSIVE trap, fires at normal 420px,
  forces result cards to 70x112. Mostly inert because popup.js sets card size
  via inline style (which beats CSS), but it is the same class of landmine.
- `@media (max-height: 500px)` ~1803: now dead code (height is 600).

Base card sizes (for reference when rescaling):
`.result-cards .tarot-card` / `.card-3d-wrap` = 90x140; `.tarot-card` = 80x126.

## Round 5 (committed `0ceb602`) — popup shrunk 420x600 -> 300x428

User picked option 1 (zoom + delete media queries + font compensation).

1. `body { zoom: 0.714; }` — 300/420 = 0.714; renders 420x600 as 300x428.
   Layout-level (vector), fonts stay crisp. 6200-line CSS untouched otherwise.
   IMPORTANT: zoom does NOT change the CSS viewport — it stays 420x600, so
   media queries still evaluate against 420x600. That is exactly why the
   `@media (max-width:420px)` trap had to be DELETED, not kept.
2. Deleted both remaining media queries (`max-width:420px`, `max-height:500px`).
   Card sizes are now solely popup.js inline styles.
3. Font compensation (147 decls): 10/11/12/13px -> 14/15/16/17px.
   Keeps 1px steps so hierarchy survives; renders 10.0/10.7/11.4/12.1px.
4. Separately bumped 8 real-content 9px rules -> 14px.
   Left 6-8px decorative diagram labels alone (containers only 36-56px wide;
   enlarging them would overflow).
